This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

LDB (Language Database) is a native Android app (Kotlin) for building and testing a personal vocabulary: words are grouped into categories ("Cats"), each word can carry a translation, example, translation of the example, and a definition, and the app quizzes the user on unacquired words over time. Package: `com.berni.android.prototype1lanbase`, single Gradle module `app`.

## Build / lint / test commands

Standard Gradle Android wrapper commands, run from the repo root:

- Build debug APK: `./gradlew assembleDebug`
- Build release: `./gradlew assembleRelease`
- Install on connected device/emulator: `./gradlew installDebug`
- Run local (JVM) unit tests: `./gradlew test`
- Run a single local unit test class: `./gradlew test --tests "com.berni.android.prototype1lanbase.ExampleUnitTest"`
- Run instrumented (on-device) tests: `./gradlew connectedAndroidTest`
- Clean build: `./gradlew clean`

Note: `app/src/test` and `app/src/androidTest` currently contain only the default boilerplate example tests generated by Android Studio — there is no real test suite to model new tests after; use standard JUnit4/Espresso/Room-testing conventions.

Compiled against `compileSdkVersion 36` / `targetSdkVersion 36`, `minSdkVersion 25`, Kotlin 2.3.10, Java 17 source/target compatibility, AGP 9.2.0, Gradle 9.6.1. `gradle.properties` sets `android.builtInKotlin=false` / `android.newDsl=false` to keep the classic `kotlin-android` + `kapt` plugins working, since AGP 9's new built-in-Kotlin path doesn't support kapt yet (still needed for Room's annotation processor).

### Running `./gradlew` from the CLI

The system default `java -version` on this machine is 1.8, which is too old for Gradle 9.x — point `JAVA_HOME` at Android Studio's bundled JBR (JDK 21) instead, e.g. `JAVA_HOME=/snap/android-studio/<build>/jbr ./gradlew assembleDebug` (find the exact path with `ls /snap/android-studio` if the build number has changed). `local.properties` already points `sdk.dir` at `~/Android/Sdk`.

### Running the app on an emulator

No AVD/system image/emulator `cmdline-tools` existed in this environment by default — only `platform-tools` and the `android-36.1` platform were preinstalled. To boot the app headlessly from the CLI end-to-end:

1. Download & unzip Android cmdline-tools (`commandlinetools-linux-*_latest.zip` from `https://dl.google.com/android/repository/...`) into `$ANDROID_HOME/cmdline-tools/latest/` (must be that exact subdirectory name for `sdkmanager` to recognize it).
2. `sdkmanager --licenses` (accept all), then install a system image matching the host arch — `sdkmanager "system-images;android-36;google_apis;x86_64" "platform-tools" "emulator"` (checked `uname -m` / `/dev/kvm` first — this host is x86_64 with KVM available, so x86_64 images run hardware-accelerated).
3. `avdmanager create avd -n <name> -k "system-images;android-36;google_apis;x86_64" -d pixel_6`
4. `emulator -avd <name> -no-window -no-audio -no-boot-anim -gpu swiftshader_indirect &`, then poll `adb shell getprop sys.boot_completed` until it returns `1`.
5. `adb install -r app/build/outputs/apk/debug/app-debug.apk`, `adb shell am start -n com.berni.android.prototype1lanbase/.ui.MainActivity`.

For driving the UI via `adb shell input tap`: **don't estimate coordinates from a screenshot** — several layouts here (e.g. `activity_tutorial.xml`'s `btn_tutorial_next`/`btn_tutorial_back`, `fragment_first.xml`'s `btn_add`) combine a ConstraintLayout guideline constraint with a large `layout_marginStart`/`marginTop` in a way that shifts the actual touchable bounds well away from where the rendered icon visually appears to be. Use `adb shell uiautomator dump` and grep the target `resource-id` for its real `bounds="[x1,y1][x2,y2]"` instead.

## Architecture

**Layers**: `db` (Room persistence) → `Repository`/`RepositoryImpl` → `MainViewModel` → UI (`Fragment`s under `ui/`), wired together with Kodein-DI rather than Hilt/Dagger.

- **Dependency injection (`LanApplication3.kt`)**: The `Application` class exposes a lazy Kodein-DI (7.x, package `org.kodein.di`) container binding `LanDataBase`, `CatDao`, `Repository` (singleton `RepositoryImpl`), and a `ViewModelFactory` provider. Fragments/activities implement `DIAware` and pull dependencies with `by instance<...>()` via `closestDI()`. There is one shared `MainViewModel` instance per screen, always obtained through `ViewModelProvider(this, viewModelFactory)`.
- **Persistence (`db/`)**: Room database `LanDataBase` with two entities, `Cat` (category) and `Word` (vocabulary entry), plus a `@Relation`-based `CatWords` projection. `CatDao` defines all queries (many return `LiveData` for reactive screens, others are plain suspend/blocking calls used from coroutines). Schema history is exported to `app/schemas/`; DB version is currently 2, with `MIGRATION_1_2` defined inline in `LanDataBase.kt` — bump the `@Database(version = ...)` and add a new `Migration` object (see the commented-out example in `Tools.kt`) whenever entity columns change, don't just wipe the schema.
- **Repository (`db/Repository.kt` / `RepositoryImpl.kt`)**: Thin pass-through interface over `CatDao`, giving the ViewModel a single collaborator. `RepositoryImpl` is itself a manually-implemented singleton (`getInstance`), in addition to being bound as a Kodein singleton — the DI binding is what's actually used by the rest of the app.
- **ViewModel (`ui/viewmodel/MainViewModel.kt`)**: One shared ViewModel exposing all read/write operations against `Repository`, plus `LiveData` properties (`allCats`, `allWords`) that fragments observe directly.
- **UI (`ui/`)**: Fragment-based single-Activity app (`MainActivity`) navigating via the Jetpack Navigation component graph in `res/navigation/nav_graph.xml`, starting at `FirstFragment`. All fragments extend `BaseFragment`, which implements `CoroutineScope` (a `Job` + `Dispatchers.Main`) so DB calls can be launched as coroutines and are cancelled in `onDestroy`. Views are accessed through generated ViewBinding classes (`_binding`/`binding` pattern, cleared in `onDestroyView`) — `kotlin-android-extensions`/`kotlinx.android.synthetic` were removed since Kotlin no longer supports that plugin.
  - `ui/test/` — the quiz flow: `Test1Fragment` (picks up to 15 random words due for testing) → `Test2Fragment` (asks questions) → `Test3Fragment` (results), feeding words along via nav-graph `Bundle` args (`testWords`, `resultTest`).
  - `ui/statistics/` — `StatisticsFragment` → `Statistics3Fragment` → `Statistics4Fragment`, charts built with AnyChart.
  - `ui/tutorial/` — a separate `TutorialActivity` shown on first launch (gated by `Tutorial.firstTime` combined with whether any category already exists, checked in `MainActivity.onCreate`). Its `setSupportActionBar(findViewById(R.id.toolbar))` call references an id that doesn't exist in `activity_tutorial.xml` — harmless pre-existing dead code (`findViewById` returns null, `setSupportActionBar(null)` just clears the action bar), not a regression, don't "fix" it without checking whether the caller actually wants a toolbar there.
  - `ui/adapter/` — `CatAdapter` / `WordAdapter` RecyclerView adapters for the two list types.
- **Shared layout quirk**: `AllWordsFragment` and `WordsListFragment` are different screens (all words vs. words-in-one-category) but both inflate the *same* `fragment_all_words.xml` / `FragmentAllWordsBinding` — `nav_graph.xml` references a `fragment_words_list.xml` that doesn't exist (`tools:layout` is just an editor hint, unused at runtime). Pre-existing, not a bug introduced by the ViewBinding migration; keep both fragments' binding usage in sync if you ever touch that layout.
- **`Tools.kt`**: grab-bag of top-level extension functions used across fragments — keyboard show/hide, `Word` list filtering (by example/definition/acquired presence) and sorting (alphabetical, by length, by date added). `limitNotAcquired` / `limitWarning` here control quiz/warning thresholds and are duplicated as literal numbers in `strings.xml` — keep both in sync when changing them.
